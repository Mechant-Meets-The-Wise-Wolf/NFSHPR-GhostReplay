# 版本、仓库与发行包的关系

这份文档回答一个具体问题：**本机目录、git 仓库、发行 ZIP 里的文件，为什么看起来不完全一样，怎么保证该一致的地方一致。**

## 1. 三层文件

| 层 | 位置 | 内容 |
| --- | --- | --- |
| 工作区 | `E:\DevTools-LoushShinny\Projects\HPRGhostReplay` | 全部文件：`src/` 源码、`app/` 可运行本体、构建产物、`research/` 证据、录像、日志 |
| 仓库 | `.git` 跟踪的部分 | 源码、脚本、数据表、文档、许可、`app/` 下的 EXE 与启动器、发行 ZIP |
| 发行包 | `releases\HPRGhostReplay-0.1-win-x64.zip` | 仅 EXE、`使用说明.txt`、`第三方许可.txt` 和空 `Recordings/` |

三者是逐层收窄，不是三份不同的代码。每个目录的具体归属见 [文件索引.md](文件索引.md)，机制细节见下文。

## 2. 哪些地方必然不同

1. **被忽略的文件只在工作区存在。** `research/`（约 565 MB）、`archive/migration-20261020/`、录像、日志、`HPRGhostReplay-dev.exe` 都不入库，规则见 `.gitignore`。克隆到新机器上不会有这些内容，需要时单独拷贝或重新生成。
2. **文本换行可能被归一化。** `.gitattributes` 设了 `* text=auto`，仓库按 LF 存储，Windows 检出时可能转成 CRLF。只影响文本，EXE/ASI/ZIP 等二进制不做转换。若 `git status` 提示文本被修改但内容没变，先查 `core.autocrlf`。
3. **重建不等于原字节。** 同一份源码重新编译，PE 头里的时间戳和编译器版本会让 EXE 哈希变化。所以"哈希相同"只证明是同一份产物，不能证明构建可复现。

## 3. 必须保持一致的地方

- `app/HPRGhostReplay.exe` 与发行 ZIP 内 `HPRGhostReplay/HPRGhostReplay.exe`：**必须同哈希**。`Package.ps1` 直接复制 `app/` 下的 EXE，正常情况下天然一致。
- `VERSION` 里的四个哈希与磁盘上的 EXE、ASI、加载器、ZIP：**必须一致**。
- `src/AppPaths.cs` 的 `AppInfo.Version` 与 `VERSION` 的 `version`：**必须一致**，否则界面标题、程序属性和包名会对不上。
- `Package.ps1` 的版本正则与版本格式：**必须一致**，否则打包会直接失败。

## 4. 日常怎么操作

| 场景 | 步骤 |
| --- | --- |
| 只改文档 | 直接提交，不需要重新构建 |
| 改源码 | 构建 → 离线自检 → `Package.ps1` → 用新哈希更新 `VERSION` 与 `docs/存档-<版本>.md` → 同一次提交 |
| 发布新版本 | 先改 `VERSION` → 同步 `AppPaths.cs`、`UiText.cs` → 构建 → 打包 → 更新 `releases/LATEST.zh-CN.txt` → 提交 → 打标签 |
| 只想确认当前是否一致 | 运行 `tools/Verify-Archive.ps1` |

不要在 `releases/` 里手工改 ZIP 或 SHA256 文件；它们由 `Package.ps1` 生成。二进制文件只在发布提交里更新，避免不可读的 diff。

## 5. 校验脚本

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\Verify-Archive.ps1
```

它会依次检查：

1. `app/` 下的 EXE、`native/bin` 里的 ASI 与加载器是否匹配 `VERSION`。
2. EXE 的 Windows 文件版本是否符合 `exe_file_version`。
3. 发行 ZIP 是否匹配 `package_zip_sha256`。
4. ZIP 内的 EXE 是否与 `app/` 下的 EXE 同哈希。

全部通过时退出码为 0；任何一项不一致会打印 `expected` 与 `actual` 并以 1 退出。
